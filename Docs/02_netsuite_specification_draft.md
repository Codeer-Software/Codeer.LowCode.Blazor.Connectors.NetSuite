# Codeer.LowCode.Blazor.Connectors.NetSuite — 仕様案

- 文書ID: SPEC-01
- 作成日: 2026-11-13
- 版: 0.1（レビュー用たたき台）
- 対応文書: [利用API調査 API-01](01_netsuite_api_inventory.md)
- 実装担当: Claude Codeを想定

> **CLBのModuleをNetSuiteのレコードに結び付け、既存のフィールド・検索・一覧・編集操作を利用できるようにする。利用者がNetSuite APIの入出力を別途二重定義することは、標準の使い方にしない。**

本書は「利用者が何を設定でき、画面とデータ操作がどう動くか」を定める仕様案である。クラス構成、内部インターフェース、DI、ルーティング位置、保存JSONの具体形式は次の設計工程で定める。以下の「必須」は仕様案を採用した場合の要件であり、既に実装済みという意味ではない。

## 1. 決定済みの方向性と今回の提案

### 1.1 ユーザーの方針として引き継ぐもの

| 項目 | 方針 |
|---|---|
| 名称 | `Codeer.LowCode.Blazor.Connectors.NetSuite` |
| 開発の参考 | `Codeer.LowCode.Blazor.Extras`の拡張ライブラリとしての作り方 |
| 主目的 | CLBのModuleとNetSuite側の設定をシームレスに結び付ける |
| 設定の操作感 | 既存のDbAccess設定の仕組み・UIを活かす |
| 実行時の処理 | NetSuite対象のGetList／Submitを、通常のDB処理ではなく専用処理へ流す |
| 避ける構造 | WebApiField＋APIごとの固定Input／Output Moduleによる二重設定 |
| 外部依存 | CDataを前提にしない |
| 実装 | 調査と仕様の整理後、Claude Codeに任せる |

### 1.2 本書で追加する提案

認証をOAuth 2.0 M2Mとすること、共通／Designer／Serverの分離、初期対応範囲、保存単位、未対応機能の扱いは本書の提案であり、ユーザーの確定済み判断と混同しない。

「シームレス」とは通常の操作にAPIの都合を露出させないことであって、外部サービス固有の権限・処理時間・対応範囲・トランザクション差を隠すことではない。

## 2. 利用者が得られる体験

### 2.1 新しいModuleを作る流れ

1. 管理者がサーバーにNetSuite接続を登録する。秘密情報はデザインへ入れない。
2. Designerでデータソースとして登録済みNetSuite接続を選ぶ。
3. NetSuiteから取得した標準／カスタムのレコード一覧から対象を選ぶ。
4. 利用する項目を選択する。型と参照先に基づきCLBフィールドの候補が提示される。
5. 一覧・詳細・検索画面を通常のCLBの操作で作る。
6. アプリでは通常の検索・詳細表示・保存を行うと、対象のデータがNetSuiteから取得／更新される。

利用者がURL、HTTPメソッド、認証ヘッダー、JSONの入出力Module、一覧用SQLを毎回組み立てることは標準手順に含めない。

### 2.2 既存Moduleを結び付ける流れ

既存Moduleでも、接続先と対象レコードを指定し、既存フィールドとNetSuite項目の対応を設定できる。自動候補は提示するが、表示名の類似だけで書込対応を確定しない。

保存前に型の不一致、必須項目の不足、読み取り専用項目への書込、未対応の検索条件等を表示する。既存のレイアウト・スクリプト・フィールド名を無断で作り直さない。

### 2.3 明示的に対象外とするもの

NetSuiteの画面をそのまま複製すること、フォームの配置やクライアントスクリプトを移植すること、NetSuite側のレコード種別／項目定義をCLBから自動作成することは初期版の目的ではない。標準動作でローカルDBへ全データを複製・同期する製品にもしない。

## 3. 提供範囲と導入形態

Extrasには共通・Designer・Serverの分離があり、メール機能でもデザインと送信インフラ設定が分かれている。本コネクターでもその考え方を参考にする。[G01] [G02]

| 提供単位の案 | 利用者に提供する役割 |
|---|---|
| `Codeer.LowCode.Blazor.Connectors.NetSuite` | デザインと共有する定義・値の表現等。秘密情報を含めない |
| `Codeer.LowCode.Blazor.Connectors.NetSuite.Designer` | 接続選択、レコード・項目選択、対応付け、定義更新・検証 |
| `Codeer.LowCode.Blazor.Connectors.NetSuite.Server` | 認証、メタデータ取得、データ操作、認可・監査との統合 |

これは配布責務の案であり、プロジェクト構成を確定するものではない。Extras全体への依存を必須とするかも設計時に判断する。

サーバー処理はWPF依存にしない。Designerは既存CLBに合わせたWindows用の統合とする。初期検証ホストはBlazor Webアプリとし、既存のUI部品を使うためだけにNetSuite専用の入力・一覧部品を大量に新設しない。

## 4. 接続設定

### 4.1 設定項目

以下は論理的な項目名であり、最終的なJSONプロパティ名ではない。

| 項目 | 設定者 | 必須 | 内容 |
|---|---|---|---|
| 接続識別名 | 管理者 | 必須 | Moduleから参照する安定した名前 |
| 表示名 | 管理者 | 任意 | Designerに表示する名称 |
| 環境 | 管理者 | 必須 | 本番／Sandbox等の区分 |
| サービスURL | 管理者 | 必須 | NetSuiteのアカウント固有URL |
| Client ID／Certificate ID | 管理者 | 必須 | M2M接続の識別情報 |
| 秘密鍵の参照先 | 管理者 | 必須 | サーバー内の保管先。デザインへは保存しない |
| 接続の利用を許可する範囲 | アプリ管理者 | 必須 | アプリ／テナント／利用者ロール等 |
| タイムアウト・同時実行上限 | 運用管理者 | 既定値あり | NetSuiteの契約・他連携を考慮して調整 |
| メタデータ更新方針 | 管理者 | 既定値あり | 明示更新、キャッシュ期限等 |

OAuth 2.0 Client Credentialsは証明書とEntity／Roleのマッピングを使う。NetSuiteで実行される主体と、CLBにログインした個々の利用者は別である。[O05] [O07]

### 4.2 接続確認

接続テストは「認証」「メタデータ参照」「対象レコードの読取能力」を分けて表示する。認証成功だけで全CRUD対応と表示しない。接続テストで本番データを作成・更新・削除しない。

Designerは保護された管理経路でサーバーに接続情報・メタデータを問い合わせる案を標準とする。取得済みの非秘密メタデータを使ったオフライン編集を許可し、未接続／未更新であることを表示する。具体的な管理APIの設計は後続工程に委ねる。

本番とSandboxは明確に区別し、切替で既存のinternal ID対応を自動移行しない。M2M設定はSandbox refresh後に再設定が必要になるため、接続診断で識別できるようにする。[O07]

## 5. DesignerでのデータソースとModuleの設定

### 5.1 DbAccess UIの流用

既存の「データソースを選ぶ→対象を選ぶ→項目を対応付ける」という操作を維持する。NetSuite側の対象は物理DBテーブルではなくレコード種別であることが分かる表示にする。

DB用設定のすべてが使えるように見せない。NetSuiteで扱えない任意SQL、DB方言、DB結合、DBトランザクション等の設定は無効化するか対象外と表示する。

現行CLBのどの公開拡張点でこのUIを流用できるかは未検証。利用可能な拡張点を確認し、不足する場合は最小限の本体拡張を設計案として分離する。NetSuite固有処理を本体へ大量に混入させない。

### 5.2 Module単位の設定

| 項目 | 標準の動作 |
|---|---|
| データソース種別 | NetSuite |
| 接続識別名 | 登録済み接続から選ぶ |
| レコード種別 | 接続先メタデータから選ぶ |
| 主キー | NetSuite internal ID。アプリ側では欠落・丸めなく保持 |
| 利用項目 | 必要な項目だけを選択 |
| 一覧の対応状態 | 対応／制限付き／未対応を表示 |
| 操作許可 | 参照・作成・更新・削除を個別に設定 |
| 固定条件 | そのModuleが扱うレコードの範囲を定める |
| 明細・参照設定 | メタデータと対応済み機能から候補を提示 |
| 外部IDによる連携 | 必要な用途だけで明示的に有効化 |

1つの通常編集Moduleは、1つのNetSuiteルートレコード種別に結び付ける。複数の独立レコードを合成した結果を、そのまま書込可能なModuleにしない。

通常DBのModuleとNetSuiteのModuleは同じアプリ内に共存できる。ただしデータソースを跨ぐ結合・集計・一括保存の保証は別に扱う。

## 6. 項目の取り込み・対応付け

### 6.1 標準の対応

| NetSuite側の情報 | CLBでの扱い |
|---|---|
| 文字列・長文 | 文字列入力／表示。最大長等が分かる場合は反映 |
| 整数・小数・金額・数量 | 精度を保つ数値入力／表示 |
| 真偽値 | チェック等 |
| 日付 | 日付のみ。タイムゾーン変換しない |
| 日時 | 時刻帯を含む日時として保持し、表示設定と分離 |
| enum | 定義済み候補の選択 |
| レコード参照 | IDと表示名を分離したSelect／Link相当 |
| 複数選択 | 対象型の契約を確認した範囲で対応。未対応なら編集不可 |
| サブレコード | 親に属する項目群として扱う。独立レコードと区別 |
| サブリスト | 閲覧用の明細。編集は対象別の対応状態に従う |
| 計算・読み取り専用項目 | 表示専用。改ざんされた要求でも書き込まない |
| 未知の型 | 未対応を表示。勝手に文字列として書き戻さない |

具体的なCLBフィールドクラスの割当ては対象版の既存機能で決める。日付と日時の区別にはNetSuiteの公式契約を適用する。[O31]

### 6.2 二重定義の防止

利用者が設定するのは「CLBフィールドとNetSuite項目の対応」1組を基本とする。詳細取得／保存のJSON名とSuiteQLの一覧列の違いはコネクター側で解決する。

ただしREST Metadata CatalogだけでSuiteQLの全対応が自動確定するとは保証しない。未確認の対象は対応情報の追加・検証を必要とし、通常の画面利用者にSQL設定を要求しない。専門開発者向けの追加対応方法は別の拡張仕様とする。[O02] [O09] [O10]

### 6.3 表示名・必須条件・初期値

NetSuiteの表示名が取得できれば候補に使い、CLB側で日本語等の表示名に変更できる。安定した対応キーには表示名ではなくAPI上の識別子を用いる。

取得できる必須条件・読み取り専用情報は入力制御に反映する。ただし業務状態による必須・計算・設定依存の検証まで完全再現するとはしない。API側のエラーをユーザーに分かる項目へ対応付ける。

NetSuite側の入力補完をすべてCLB上で即時再現する仕様にはしない。保存時に確定する値は保存後の再読込で反映する。

### 6.4 定義更新

「NetSuite定義を更新」で差分を提示する。追加項目は任意選択、削除／型変更／権限で見えなくなった項目は警告し、既存のCLBフィールドやスクリプトを自動削除しない。

書込対応を維持できない破壊的変更は保存を停止する。読取継続可能かは項目単位で判定する。取得できなくなっただけでNetSuite側から削除されたと断定しない。

メタデータ更新によって、これまで公開していない機微な項目が自動的に画面やAPIへ追加されないこと。

## 7. 一覧・検索・詳細表示

### 7.1 一覧取得

GetList相当の操作は、対象Moduleの接続設定をサーバー側で解決してNetSuite用処理へ渡す。通常DBのSQL実行へNetSuite用のテーブル名を流し込まない。

既存の一覧が必要とする行・ページ情報を返す。接続不能を「0件」として成功扱いしない。表示件数、ページ件数、全件数を混同しない。

SuiteQLで対応が確認できる場合は、必要列と必要ページをまとめて取得する。対応がない対象は制限付きRecord検索モード、または未対応として明示する。最初の画面表示のために全レコードを読み込む仕様にはしない。

### 7.2 検索・並び順

初期対応候補は、等価、不等価、大小、範囲、文字列一致／前方一致／部分一致、空値、参照ID、AND／OR。型や取得経路によって使える操作を絞る。

対応していない条件を無視して広い結果を返さない。並べ替えは検索結果全体に対して行い、現在ページだけを並べ替えて代用しない。SuiteQLの値はパラメーター化する。自由入力をSQLの一部として挿入しない。[O09]

固定条件、利用者の検索条件、行権限条件を組み合わせてからページングする。件数取得にも同じ条件を使用する。集計・検索候補・詳細取得にも同じ公開範囲を適用する。

### 7.3 ページ境界・上限

一意キーを含む安定した順序を使う。APIのページサイズ・offset・結果上限を満たすようにする。上限へ到達した場合は絞込みを促す等の明示的な結果とし、最終ページと偽らない。[O09] [O12]

外部更新を挟んだ複数ページが厳密な同時点スナップショットになる保証はしない。必要な案件は別の取得方式・業務要件として扱う。

### 7.4 詳細取得

一覧行をクリックした場合、サーバーがModule・接続・レコード種別・ID・読取権限を確認して取得する。URLやIDを直接書き換えても他の利用者のデータを読めないこと。

詳細取得では編集に必要な項目と対応済みの明細を読む。書込に必要な値が取得できない場合、空値として上書きせず編集不可にする。

## 8. 参照・選択肢

固定enumと動的な候補を区別する。動的候補は、可能な場合に`selectOptions`でNetSuite側の候補を取得する。現在の入力値に応じた候補取得が可能であり、単なる参照先の全件一覧とは区別する。[O19]

候補の値はID、表示は名称とし、表示名の重複でも正しいIDを選べること。候補の再取得で既存値が無効になった場合は確認を求め、勝手に別の先頭候補へ置き換えない。

候補は入力依存値の変更時に再評価する。どの項目に依存するかを自動確定できない場合は、対応情報または最小限の追加設定で補う。

候補取得は保存ではない。selectOptions用ヘッダーを失った通常POST／PATCHを送らないことを必須テストとする。候補取得で権限や業務データを変更しない。

参照先の詳細Moduleがない場合でも選択自体は可能な範囲で動作する。詳細へのリンクは、遷移先Moduleの権限と対応関係が確認できた場合だけ有効にする。

## 9. 新規作成・更新・削除

### 9.1 保存の基本

既存のCLB保存操作を使い、内部の行先だけをNetSuiteへ切り替える。ただし「同じボタンだからDBと同じトランザクション保証がある」とは表示しない。

| 操作 | 振る舞い |
|---|---|
| 新規作成 | 許可された項目をPOSTし、NetSuiteのIDを受け取る |
| 更新 | 対象IDの存在・権限を確認し、許可された変更項目だけをPATCHする |
| 消去 | 明示的な項目消去として扱い、未変更と区別する |
| 保存後 | 再取得して採番・既定値・計算値を反映する |
| 削除 | 対象レコードで対応し、Module設定と利用者権限が許可した場合のみ |
| 無効化 | 削除とは別の明示操作として定義した場合のみ |

PATCHの省略項目は未変更であり、nullによる消去と異なる。更新対象には画面から送られた全項目を無条件に使わない。[O15]

### 9.2 操作の許可

Moduleごとに参照・作成・更新・削除を設定できる。削除は既定で無効とする案とし、有効化してもNetSuite側の業務制約に従う。

書込可能な項目をサーバー上の定義から決定する。ブラウザーの「読み取り専用」表示だけでは制御しない。固定条件や行権限の対象外へ移動する更新も検証する。

### 9.3 IDと外部ID

主キーはinternal IDを基本とする。CLBの一時的な新規IDとNetSuiteの確定IDを区別する。別アカウントの同じ数字のIDを同じレコードとして扱わない。

外部ID連携を有効にした場合だけUpsertを使う。外部IDの採番・一意性・既存レコードとの衝突時の動作を設定する。通常の画面保存を暗黙にUpsertへ変えない。[O17] [O18]

### 9.4 保存結果の区分

最低限、「成功」「業務／入力エラー」「権限拒否」「接続／認証エラー」「保存結果不明」を区別する。

保存成功後の再取得だけが失敗した場合は「保存済み・再読込失敗」と分ける。入力値を保持し、利用者が誤って再作成しない表示にする。

## 10. 保存単位・明細・トランザクション

### 10.1 初期版の保存単位

**初期版は1つのNetSuiteルートレコードを保存単位とする案。** 同じREST要求に安全に含められると確認したサブリスト／サブレコードは、そのレコードの一部として扱う。

複数の独立したNetSuiteレコード、複数接続、NetSuiteとローカルDBが混在する1回の保存要求は、初期版では副作用を起こす前に拒否する。画面上で個別に保存することは可能でも、一括ロールバック保証は付けない。

現行Starterには`SubmitWithTransactionAsync`を使う保存経路がある。これをNetSuite用に分岐した結果、保証内容だけが黙って変わることを避ける。[G07]

### 10.2 明細の扱い

閲覧は先に対応し、追加・更新・削除はレコードとサブリストごとに対応状態を公開する。keyed／non-keyed等により更新契約が異なるため、汎用のDB明細更新として扱わない。[O20]

明細保存では以下を守る。

- 未取得・未表示の行を削除しない。
- 行キーを表示順や行インデックスで代用しない。
- 全置換しかできない場合は、その安全性を検証した対象だけで許可する。
- 不明な読み取り専用値までJSONごと送り返さない。
- カスタム親子レコードと、親レコード内のサブリストを区別する。[O22]

初期対応候補に受注明細を含める場合も、顧客のNetSuite設定・品目・税・必須値等を確認して対象プロファイルを確定する。「すべての取引明細の編集対応」とは表現しない。

### 10.3 更新競合

対象APIの原子的な競合制御は未検証。更新日時を保存前に比較するだけでは、比較と書込の間の競合は防げない。

初期版で完全な楽観ロックを保証しない。競合検出の対応状況をModuleの能力情報に表示し、同時編集による上書きを許容できない案件では、確認済みの排他方式が用意できるまで編集対象としない。

## 11. 認証・認可・監査

### 11.1 二段階の権限制御

実行可能な操作は、CLB側で許可された範囲とNetSuite接続ロールで許可された範囲の両方を満たすものとする。M2M接続が強い権限を持つからといって、CLB利用者全員にその範囲を公開しない。

サーバーは毎回、対象Module、操作、行、項目、参照先を検証する。直接APIを呼び出した要求にも同じ制御を適用する。新規作成でも、任意の会社・部門・子会社等へ書き込めないように公開範囲を検証する。

行権限を安全に適用できない取得経路は、権限を無視して続行せず未対応として拒否する。UI側での非表示や、ページ取得後の行除外だけで代用しない。

### 11.2 現行CLBとの互換性

現行StarterのControllerは認証・CSRF対策を持ち、データ処理をModuleDataIOへ委ねる。Extrasでも現在ユーザーのModuleDataIO等を文脈として渡している。[G07] [G04]

NetSuiteへ振り分ける際は、これらの認可・監査の意味を保持する。ブラウザーからの入口だけを差し替え、サーバー側スクリプトや参照候補の経路だけが通常DB処理へ流れる状態にしない。

基本経路で対応できない既存の集計・一括入出力等は、能力情報で非対応を明示する。未対応なのに通常DBへフォールバックして動かそうとしない。

### 11.3 秘密情報・外部要求

秘密鍵・tokenはサーバー内で管理し、デザインの配布物、Git、ブラウザー、標準ログへ含めない。接続先URLは管理設定を基準にし、API応答内のリンクを追う場合も許可されたホスト・パスを検証する。

ブラウザーが任意の接続名、レコード種別、URL、SuiteQL、未公開項目を指定しても拒否する。テナントを識別する値も認証済みのサーバー文脈から解決する。

### 11.4 監査

CLB利用者、接続識別名、Module、操作、対象ID、結果、時刻、所要時間、相関IDを記録できること。NetSuite側に残るM2M主体と、実際に操作したCLB利用者の対応を追跡可能にする。

要求・応答の業務データ全文を既定でログ出力しない。外部サービスの詳細エラーは管理者向け記録と画面メッセージを分け、権限のないデータや秘密情報を漏らさない。

## 12. 障害時の動作・性能

### 12.1 エラー表示

NetSuiteの項目エラーを可能な範囲でCLBフィールドへ対応付ける。対応できないエラーは保存全体のメッセージとして返す。外部エラーのコードを失わず記録し、ユーザー表示は安全な内容にする。[O29]

未対応機能、定義不一致、認証失敗、権限不足、制限超過を区別する。未知の項目が無視される保存を防ぐため、書込APIの項目名検証は厳格側で扱う案とする。[O29]

### 12.2 再試行

読取系は制御した再試行を許可する。書込の送信後に応答を失った場合は、結果不明として扱い、勝手に再作成しない。成功／失敗を確認できる手段がある場合のみ、それに基づき再実行する。

利用者がキャンセルしたことやクライアントのタイムアウトは、NetSuiteの処理が取り消された証拠にはしない。

### 12.3 API呼出し量

アカウントの他の連携と競合するため、同時実行数を設定できること。アプリが複数台でも、コネクター自身の呼出し量を把握・制御できる方式を設計する。NetSuite側の上限を固定値で決め打ちしない。[O30]

一覧でレコードごとの詳細取得が発生する場合は、経路と呼出し回数を診断可能にする。性能の数値保証は実アカウント測定後に決める。

### 12.4 キャッシュ

token、メタデータ、選択肢のキャッシュは、接続・アカウント・認証主体／ロール・設定世代で分離する。選択肢では現在値等の入力文脈も含める。別ロールで取得した項目定義・候補を使い回さない。

証明書・ロール・接続先・定義を変更した場合は関連キャッシュを更新する。障害時に古い情報を使う場合は状態を明示し、権限変更を無視した書込の継続はしない。

## 13. 初期範囲と拡張範囲の案

| 段階 | 範囲 | 条件 |
|---|---|---|
| P0：最初に成立させる範囲 | 接続設定、メタデータ選択、標準／カスタム項目対応、一覧・詳細、単一レコードのbody項目CRUD、基本参照・選択肢、権限・監査・エラー | 顧客等の検証済み標準レコードと、単純なカスタムレコードを検証セットにする |
| P1：業務範囲を拡張 | 対象別の明細編集、住所等のサブレコード、複雑な参照、外部ID Upsert | 各操作の安全性と対象プロファイルを検証 |
| P2：既存NetSuite設定の活用を拡張 | Saved Search／Datasetの読取Module、Action／Transform、ファイル、非同期 | 個別の能力・制約を定義して追加 |
| 別仕様 | 複数独立レコードの一括保存、DBとの同期・分散処理、汎用RESTlet配備、利用者別OAuth認可 | 本書から暗黙に実装範囲へ含めない |

P0は「一覧表示だけ」の検証で終わらせず、カスタム項目を含めてCLBの操作からNetSuiteへ保存できるところまでを目標とする。ただし、実アカウントに存在しないフィールドを想像で対応済みにしない。

Saved Search／Datasetを追加する場合は、読み取り専用の結果と編集可能なレコードを分ける。保存検索の条件・ソートの上書きや、Datasetメタデータの完全自動取得は前提にしない。[O23] [O24]

| AC07 | 不明な検索条件 | 無視せず未対応を返す |
| AC08 | SuiteQL入力 | 値はバインドされ、任意列名・SQLの注入ができない |

| AC11 | selectOptions照会 | レコードが作成／更新されない |
| AC12 | 新規保存 | NetSuiteのIDを取得し、再表示できる |
| AC13 | 差分更新 | 変更対象外の項目を消さない |

| AC15 | 日付・日時・金額 | 日付ずれ・不要な丸めが発生しない |

| AC17 | 接続名・レコード種別の改ざん | Module定義と認証文脈を基準に拒否する |
| AC18 | 行条件外への更新・新規作成 | 公開範囲を逸脱する書込を拒否する |
| AC19 | M2M共有下の複数ユーザー | CLBの利用者別権限が維持される |
| AC20 | NetSuite権限不足 | 不正なデータや内部情報を漏らさず区別できる |
| AC21 | 作成後の応答消失 | 自動再POSTせず結果不明として扱う |
| AC22 | 保存成功・再取得失敗 | 保存失敗と混同せず再読込を案内する |
| AC23 | 429・認証期限切れ | 上限付き再試行／再認証。無限ループや集中呼出しをしない |

| AC26 | 権限・接続変更後のキャッシュ | 別ロール・別アカウントの情報を流用しない |
| AC27 | サーバー側スクリプト・参照経路 | 対応済み操作は同じNetSuite処理と認可を通る |
| AC28 | 通常DBのModuleとの共存 | 既存DBの操作を壊さない |
| AC29 | 更新競合 | 保証できる範囲が表示され、未確認を完全対応としない |
| AC30 | 監査・診断 | CLB利用者、対象、結果を追え、秘密情報をログへ出さない |

テストはHTTPモックによる契約・異常系テストと、NetSuite実アカウントでの結合テストに分ける。後者を実行していない状態では「NetSuite接続確認済み」と表示しない。

## 16. Claude Codeへの引き継ぎ

実装着手前に、API-01、SPEC-01、対象リポジトリの実コードを読み、上記D01〜D05について設計上の回答を作る。公開資料で確認した機能と、実アカウントで確認した機能を区別する。

進め方は次を基本とする。

1. 対象バージョンと拡張点を確認し、最小の接続PoCで認証・メタデータ・SuiteQL・CRUD・selectOptionsを検証する。
2. 仕様との差を整理し、必要な設計案を作成する。既存CLB本体に必要な変更があれば別項目にする。
3. P0の範囲を実装し、受入条件と通常DBの回帰テストを実行する。
4. 対象・操作ごとの対応表、導入手順、デザイン例、制約、実機検証結果を文書化する。

**行わないこと:** 全レコード対応の一括宣言、秘密鍵を含むサンプル、任意URL／任意SQLの公開、権限チェックの省略、暗黙の明細全削除、複数APIの原子的成功の偽装、モックだけでの接続確認済み宣言。

最終成果物には、Extrasのような利用者向けドキュメントと、AIが設定・拡張に利用できるドキュメントを含める。標準利用者が読む内容は「接続→レコード選択→項目選択→画面作成」を中心とし、内部APIの説明を必須の利用手順にしない。
