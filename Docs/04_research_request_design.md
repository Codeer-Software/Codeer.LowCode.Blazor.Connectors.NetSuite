## 1. 何のための調査か

REQ-01 は「いまのコードが置いている前提が実物と合うか」を 1 つずつ確かめる依頼だった。
この依頼は別の目的で、**コネクターの作りの分岐を決めるための材料** を集める。答えによって、どこまでを 1 つの仕組みで扱い、どこを別の仕組みにするかが変わる。

REQ-01 と重なる質問 (Q-I1 / Q-I2 / Q-I3) は、この文書の質問にまとめて答えてよい。優先順は **K → P → L → M → N**。

### いま考えている全体像 (質問を読むのに必要な分だけ)

NetSuite の機能を、CLB の 3 つの経路に分けて載せるつもりでいる。

| 経路 | NetSuite の機能 | CLB での見せ方 |
|---|---|---|
| データソース | レコードの読み書き・SuiteQL の検索と集計・レコード間の参照・明細 | モジュール (1 モジュール = 1 レコード種別)。一覧・検索・詳細・保存・集計・リンクは DB のモジュールと同じ操作 |
| 設計時 | メタデータ (項目・型・必須・読み取り専用・固定の選択肢) | デザイナがレコードからモジュールを作るときに取り込む。固定の選択肢は選択フィールドの候補としてデザインに書き込む |
| 個別の機能 | 入力に応じて変わる選択肢 (selectOptions)・Action・Transform・保存検索・ファイル | 専用のフィールドやボタン。データソースには載せない |

CLB の保存の動きで、質問に関係するのは次の点。

- 画面の保存 1 回は、複数のレコードの追加・更新・削除の束としてサーバーに届く。サーバーは **1 行ずつ順に** 処理する。
- 親と明細を同時に新規作成するときは、**先に親を作って採番された ID を受け取り**、その ID を明細の各行の親 ID に入れてから、明細を 1 行ずつ作る。
- 明細は「親の ID を持つ別のレコード」として扱う。行の更新・削除は、行自身の ID で行う。
- NetSuite への書き込みは 1 件ごとに確定し、束の途中で失敗しても前の書き込みは戻らない (この点は決めてある)。

## 2. 回答の書き方

REQ-01 の「2. 回答の書き方」と同じ。加えて次の 2 点。

- 「できる / できない」を先に書く。条件つきなら、その条件 (レコードの種別・機能の有効化・ロールの権限) を書く。
- 質問の最後に **【判定】** とあるものは、調べた事実を並べるだけでなく、問いに対する結論を 1 つ書く。判定できなければ、何が分かれば判定できるかを書く。

## 3. 質問

### K. 明細・サブレコードの書き込み (最優先。作りの分岐を決める)

CLB の「親を作る → 明細を 1 行ずつ作る」という順序が、NetSuite の REST で成り立つかを知りたい。

- **Q-K1** 取引のレコード (`salesOrder` / `invoice` / `purchaseOrder` / `estimate` / `journalEntry`) を、**明細を 1 行も付けずに POST で作成できるか**。
  できないなら、種別ごとに最低限必要な明細は何か。エラーの実物。
- **Q-K2** 明細なし (または最小の明細) で作ったレコードに、あとから **PATCH で明細を 1 行だけ追加する** 要求の形。その PATCH は既存の行に影響しないか
  (keyed / non-keyed のそれぞれで。`?replace=` を付けないときの既定の動き)。
- **Q-K3** 既存の明細の **1 行だけを更新する**・**1 行だけを削除する** 要求の形。行を指定するキーは何か (`line`・`lineUniqueKey`・配列の位置など)。
- **Q-K4** 同じ親に対して PATCH を続けて N 回送る (明細 N 行を 1 行ずつ追加する) と、1 回の PATCH にまとめたときと結果が変わる場合はあるか
  (合計の再計算・税・在庫の引当・ワークフロー・スクリプトの実行回数・同時実行の制限)。**【判定】** 1 行ずつの PATCH で実用になるか、1 回にまとめるべきか。
- **Q-K5** 行のキーの対応。REST で行を指定するキーと、SuiteQL の `transactionline` (ほかの明細の表があればそれも) の列は、どれとどれが同じ値か。
  PATCH / POST で行を追加した直後に、その行のキーを知る方法 (応答に含まれるか。含まれないなら、読み直して特定する確実な方法)。
- **Q-K6** 明細の行を、親なしの独立したレコードとして読む・書く API はあるか (`record/v1/salesOrder/{id}/item/{line}` のような URL で 1 行を GET / PATCH / DELETE できるか)。要求と応答の実物。
- **Q-K7** サブレコード (`customer` の `addressBook`・住所) について Q-K1 〜 Q-K6 と同じこと。住所の行は独立した ID を持つか。
- **Q-K8** カスタムレコードの親子関係 (子のカスタムレコードが親への参照の項目を持つ形) は、子を独立したレコードとして普通に作成・更新・削除できるか
  (= 明細の扱いが要らないか)。親の画面にサブリストとして出る設定にしていても同じか。
- **Q-K9** **【判定】** 以上から、「明細を、親の ID を持つ別のレコードとして 1 行ずつ保存する」方式が、(a) そのまま成り立つ種別、(b) 親の作成と最初の明細を 1 つの要求にまとめれば成り立つ種別、
  (c) 成り立たない種別、に分けてほしい。

### P. ほかの製品の見せ方 (先例)

同じ問題をほかの製品がどう解いたかを知りたい。対象は、NetSuite をテーブルやエンティティとして見せる製品
(CData の NetSuite ドライバ・SuiteAnalytics Connect・Power Apps / Dataverse の仮想テーブルや NetSuite コネクター・OutSystems・Mendix・Celigo・Boomi・Workato・MuleSoft のうち、公開資料があるもの)。

- **Q-P1** 取引の明細を、親とは別のテーブル (エンティティ) として見せている製品はどれか。その製品で、明細のテーブルへの INSERT / UPDATE / DELETE は何に変換されるか。
  「親と明細を同時に新規作成する」場合の扱い (専用の入力形式・一時テーブル・親の INSERT に明細を JSON で埋める、など) を、製品の資料の記述のまま示してほしい。
- **Q-P2** 取引の種別 (受注・請求など) を、それぞれ別のテーブルとして見せているか、`transaction` 1 つとして見せているか。
- **Q-P3** 固定の選択肢・入力に応じて変わる選択肢を、どう見せているか (テーブル・列の属性・専用の API)。
- **Q-P4** 利用者ごとの権限と操作の記録を、製品の側と NetSuite の側のどちらで受け持つ作りか。接続に使うアカウントは共通か、利用者ごとか。
- **Q-P5** **【判定】** 複数の製品に共通する見せ方 (事実上の標準) があれば、それは何か。

### L. NetSuite 側に残る履歴

アプリの利用者は全員、連携用の 1 つのアカウント (M2M で選んだ Entity とロール) で NetSuite にアクセスする。NetSuite 側の履歴で足りる範囲を知りたい。

- **Q-L1** REST (M2M) で作成・更新・削除したレコードの System Notes には、「誰が」「どの経路で」として何が残るか (Set by・Context の値)。実物の例。
- **Q-L2** アプリの利用者の名前や ID を、NetSuite 側の履歴に残す公式の方法はあるか (要求のヘッダー・メモの項目・専用の項目に書く、など)。
- **Q-L3** System Notes を SuiteQL で読めるか (表の名前・列・必要な権限)。削除されたレコードの履歴は残るか。
- **Q-L4** REST の要求そのものの記録 (実行ログ) は NetSuite 側にあるか。保存期間と、見る方法。

### M. 利用者ごとの権限を NetSuite に任せる方式

- **Q-M1** OAuth 2.0 の Authorization Code Grant で、アプリの利用者ごとに NetSuite のトークンを取る方式は、REST Record Service と SuiteQL の両方で使えるか。
  利用者ごとに必要なもの (NetSuite のユーザーライセンス・ロール)。リフレッシュトークンの期限と、切れたときの再同意。
- **Q-M2** M2M のまま、1 つのインテグレーションに複数のロール (複数の証明書とマッピング) を登録して、要求ごとに使い分けられるか。
- **Q-M3** SuiteQL の結果に、実行したロールの権限 (レコード種別・子会社・部門などの制限) はどう効くか。権限の無い行は黙って除かれるか、エラーになるか。

### N. データソースに載せない機能

- **Q-N1** `selectOptions`: 要求と応答の実物 (新規・既存)。候補が多いときのページングと絞り込み。ある項目の候補がどの項目の値に依存するかを、API から知る方法はあるか (REQ-01 の Q-I1 を含む)。
- **Q-N2** Action (`@{action}`): レコードの種別ごとに使える Action の一覧の出所。要求と応答の実物を、承認の例で。
- **Q-N3** Transform (`!transform`): 対応する変換元・変換先の組み合わせの一覧の出所。要求と応答の実物を、受注 → 請求書の例で。変換と同時に値や明細を変える書き方。
- **Q-N4** 保存検索・Dataset の結果 (`savedsearch/{id}/result`・`dataset/{id}/result`): 応答の実物。列の名前と型はどこで分かるか。ページングの方法と上限。
- **Q-N5** 固定の選択肢 (`entityStatus` のような enum、`customlist_xxx` のカスタムリスト) の候補の一覧は、メタデータから全部取れるか。SuiteQL で読める表はあるか。
