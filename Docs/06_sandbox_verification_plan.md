## 1. 実施条件と証跡

### 1.1 環境の記録

各テストには、アカウント、Sandbox名、NetSuiteリリース／適用済み月次更新、時刻とタイムゾーン、Integration ID、Entity ID、Role ID、認証方式を付ける。証明書IDは運用上許容される範囲で管理し、秘密鍵・アクセストークン・リフレッシュトークンは記録しない。

REST Web Services、OAuth 2.0、SuiteAnalytics Workbook、A/R、Purchase Orders、SuiteTax、OneWorld、Multi-Book、Advanced Approvals等の該当設定を保存する。カスタム必須項目・フォーム・User Event・Workflow・Bundle/SuiteAppの有無も記録する。

本番の実顧客・実注文ではなく、検証専用の顧客・取引先・品目・勘定・住所を使う。メール、外部連携、在庫処理、承認通知への副作用を事前に確認する。既存監査ログを削除するなどの後処理は行わない。

### 1.2 1ケースにつき保存するもの

```text
case-id/
  environment.json
  metadata.openapi.json
  metadata.schema.json
  request.http.redacted
  response.headers.redacted.txt
  response.body.json
  before.record.json
  after.record.json
  before.suiteql.json
  after.suiteql.json
  system-notes.csv
  findings.md
```

不要なファイルは省略してよい。ただし「何を送ったか」「HTTPとエラーの実物」「保存前後の状態」「実行ロール」は省略しない。HTTP 204なら本文を捏造せず「空」と記録する。GETにページングがあれば全ページを保存する。サンプルJSONと実測JSONはファイル名でも分ける。

`findings.md`には、仮説、操作、実測結果、判断、適用可能範囲、他テナントへ一般化できない条件を書く。成功1回だけで、並行更新や他の行種別にも同じと断定しない。

### 1.3 共通の安全策

自動リトライは、書き込みの結果不明時に無条件で行わない。タイムアウト後に新規行のPOST/PATCHを再送すると重複する可能性があるため、先に相関ID・親ID・保存後GET等で結果を確認する。対象型で利用できるExternal IDや専用行相関項目も、実際の対応を確認してから使う。

ロールを弱めるテストと、更新・削除を伴うテストは検証用設定だけで行う。認可エラーを回避するために常用ロールをAdministratorに昇格させる方式は採らない。

## 2. 最優先: CLB側の保存契約

### T-C01 — 画面保存の束を親単位にまとめられるか

**対象: K4/K9。NetSuite接続前にコード側で確認する。**

同じ画面保存で、新規親1件・明細3件、既存親への明細追加／更新／削除、親2件に跨る変更をそれぞれ作る。CLBがどの段階で変更集合を保持し、いつ親IDや子IDを必要とするかをコードとログで確認する。

確認事項:

- NetSuiteへ送る前に、同じ親に属する変更行を全て取得できるか。
- 仮の親／子IDを、NetSuite保存後のIDへ置き換える仕組みがあるか。
- 初回親POSTに明細を同梱してから、子行の個別POSTが二重に走らないよう制御できるか。
- 親単位の成功・失敗を元のCLB行へ対応付けられるか。
- 親A成功・親B失敗を、全体失敗として隠さず表示できるか。

**判定:** 集約できるなら明細保存経路を追加する仕様を採る。集約できないなら、対応する拡張点を先に作るか、取引明細の通常保存を初期対象から外す。ダミー成功や架空のNetSuite IDで既存契約を誤魔化さない。

## 3. K: 明細・サブレコード

### T-K01 — ゼロ明細作成と最小条件

対象はsalesOrder、invoice、purchaseOrder、estimate、journalentry。

| ケース | 送るもの | 目的 |
|---|---|---|
| A | 有効なヘッダーだけ。明細プロパティなし | 空親が作れるか |
| B | 同じヘッダー＋明細`items: []` | 省略と明示的空配列の差 |
| C | 商品取引は有効な1明細、仕訳は均衡する2明細 | A/Bが失敗しても接続・ヘッダー不備と混同しない対照試験 |
| D | 仕訳に借方1明細のみ | 均衡条件の実エラー |
| E | 請求書でitemなし、適用可能なitemcost又はtimeあり | 「itemが空」と「請求明細が全くない」の区別 |
| F | 発注のitemのみ／expenseのみ | PO公開ヘルプの矛盾を解消 |

Cが成功しない場合はA/Bの失敗を「明細が必須だから」と断定しない。必須項目・ロール・税・スクリプト等を先に確認する。エラーのHTTP status、`o:errorCode`、detail、対象フィールドパスをそのまま保存する。

**合格条件:** 種別ごとに最小成功ペイロードとゼロ件時の失敗／成功を再現でき、理由が切り分けられている。スクリプトが自動的に明細を入れた場合は「空明細の親が保存できた」と記録しない。

### T-K02 — keyed／non-keyedの既定PATCH

keyedサブリストをメタデータで確認し、2行の親を作る。`replace`なしでキー省略の1行を追加し、既存2行・追加1行・合計・キーを確認する。既存キー付きの更新も行い、重複追加されないことを確認する。

実際に書き込み可能なnon-keyedサブリストを選び、同様に追加要求を行う。種類を確認できなければ検証未実施とし、便宜上keyedをnon-keyedとして扱わない。

**合格条件:** 省略行の保持、キー一致更新、追加の条件を対象型ごとに説明できる。構造上の保持と、計算値／スクリプト変化は別に記録する。

### T-K03 — 1行更新・1行削除・置換

3行の取引で中央行を更新する。その後、残す2行だけを指定する`?replace=item`を実施する。キーのみで残存行が保持されるか、必須値も必要かを検証する。仕訳では均衡を維持する2行単位の変更・削除も試す。

件数がページサイズを超える親でも試す。1ページ分しか取得していない状態では、置換を実行せず安全に拒否する。

**合格条件:** 対象以外の明細が消えず、読み取り専用項目を送らない書き込み形式が決まっている。削除不能な状態（出荷済み、請求済み等）のエラーを別に扱える。

### T-K04 — 逐次N回と1回集約の差

同じ条件の検証用親A/Bを用意し、Aに明細を1行ずつ10回追加、Bに同じ10行を1回で追加する。仕訳は1行ずつの非均衡更新と、均衡する集約更新を対比する。

比較するものは、明細、ヘッダー合計、税、ステータス、引当関連値、System Notes、対象スクリプトの実行記録、外部通知、所要時間、要求件数。ワークフローの有効／無効を無断で変えず、条件を揃える。

**判定:** 結果が一致しても、そのテナント・型・設定での成立に留める。汎用仕様は親単位集約を既定とする。直列N回の要求数と同時実行数を混同しない。

### T-K05 — REST明細キーとSuiteQL列の対応

同じ品目・数量を含む重複行をあえて作る。REST明細の全フィールド／self URLと、SuiteQLのtransactionline候補列を比較する。

次の各段階で採取する: 初回作成、途中行削除、行追加、UIでの並べ替え、同じ品目の複数行追加、可能なら複製／Transform。品目IDだけで照合しない。

| REST側 | SuiteQL側の確認候補 | 記録事項 |
|---|---|---|
| 親ID | transaction | 同じ親を指すか |
| line等の公開キー | id | 全行で一致するか、削除後も安定するか |
| lineUniqueKeyが公開される場合 | uniquekey | 値と用途が一致するか |
| 配列順 | linesequencenumber | 変化する順序情報か |
| 独自相関項目 | 同じcustcol項目 | 追加後に一意対応できるか |

**合格条件:** 型・サブリスト別の対応表が実測付きで存在する。追加行が複数・重複でもCLB仮IDに対応できるか、できない条件を明示する。未確認の対応を共通マッピングとして実装しない。

### T-K06 — 直接サブリソース操作と同時更新

OpenAPIに表示されるメソッドを確認し、GET、必要に応じPATCH、DELETEの公開範囲を検証用レコードで記録する。未公開メソッドを製品の通常処理には使わない。削除は親置換を基本とする。

競合試験は、クライアントAが全行GET→Bが行追加／変更→Aが古い状態から置換、の順で実施する。競合を検出して拒否できるか、Bの変更が失われるかを確認する。NetSuite側に実際の条件付き書き込み契約が確認できない限り、比較GETだけで原子的保護を実現したと扱わない。

**合格条件:** サブリソースURLの存在と完全CRUDを混同せず、置換競合時の製品仕様が決まっている。

### T-K07 — 住所録行と住所サブレコード

住所なしcustomerを作り、住所を2件追加する。各住所録行のキー、住所サブレコードのキー／URL、デフォルト請求／配送先を記録する。片方だけ変更・削除し、もう片方とデフォルト属性への影響を見る。

サブレコードnull化が許される場合でも、「住所を空にする」と「住所録行を消す」を区別する。SuiteQL上で住所を参照できるなら、その表・列・親関係も照合する。

**合格条件:** addressBookの行とaddressBookAddressの違い、キー項目、保存形、削除形が実物で確定する。

### T-K08 — 独立カスタム親子

親型と子型を作り、子に親参照を設定し、親画面にサブリスト表示する。RESTで親作成→子3件を順に作成→子単独更新→子単独削除→親で子を絞り込み取得を行う。

**合格条件:** 子の独立IDと通常CRUDを確認。親画面の表示設定がRESTの書き込み単位を変えないことを確認する。独自スクリプトや親削除時の制約は別仕様として記録する。

## 4. L: 履歴と監査

### T-L01 — 共通M2MのSet by／Context

CLB利用者A/Bが同じM2M接続を使って、異なる値を作成・更新する。NetSuiteのSystem Notes UI、SuiteQL、REST実行ログを比較する。`Log System Notes on Updates Only`の状態を記録し、新規・更新・削除を分ける。

**合格条件:** NetSuiteが記録する主体と、CLB側で別途記録すべき主体が区別できる。表示名・内部コード・Roleを実測で示せる。

### T-L02 — 外部利用者IDと相関ID

認証済みの利用者A/Bからの操作に、サーバー確定のactor IDと一意のrequest IDを付ける。クライアント側で他人のactor IDへ改変した入力が、サーバー側の確定値を上書きできないことも確認する。

同じ利用者の連続操作、NetSuite更新成功後のCLBログ書込み失敗、監査用レコード成功後の本体更新失敗、DELETEを試す。

**合格条件:** 「最後の更新者」と「操作履歴」を区別し、部分失敗時も相関可能。カスタム項目がSet byを変更するという誤った説明がない。

### T-L03 — SystemNote権限と削除後の記録

System Notes for Analytics and RESTを持つロール／持たないロールで同じSQLを実行する。自身の変更・他者の変更がどう返るかを比較する。

通常System Notes対象とSystem Notes v2対象を分け、削除前後で履歴を取得する。Deleted Recordの対象型・必要機能・権限も確認する。

**合格条件:** 「全件」「自身のみ」「未対応」「権限エラー」を区別できる。削除前の変更履歴が残ると誤って保証しない。

### T-L04 — REST実行ログの保存期間

REST Web Services実行ログの表示項目と最古の閲覧可能日時を確認する。ただし、最古レコードの日付だけで保持期間の上限を推定しない。ログがその日以降しか発生していない可能性がある。

保持期間については対象アカウントに適用されるOracleの回答・設定・公式資料を保存する。SOAP/MCP/SuiteScriptの説明と区別する。

**合格条件:** 確定できた期間を適用条件付きで示すか、「未確定・CLB側で独立保持」と明示する。

## 5. M: 認証と権限

### T-M01 — 利用者別Authorization Code

利用者A/Bに異なる適切なロールを付与し、それぞれの認可でRecord GET/PATCHとSuiteQLを実行する。本人のデータ範囲とSystem Notes主体を比較する。NetSuiteユーザーとCLBユーザーの対応を取り違えないことを確認する。

トークン有効期限・refresh条件を実レスポンスと設定で確認する。失効／同意取消しは検証用トークンで試し、無限リトライせず再認可へ誘導する。通常クライアントとPublic clientの条件を分ける。

**合格条件:** 同意・認可・更新・失効の動作と、ライセンス／ロールの前提が説明できる。

### T-M02 — 同一Integrationの複数M2Mマッピング

同じIntegrationで、Role A・Role Bに別証明書を対応させ、取得トークンごとのデータ範囲と記録主体を確認する。

キャッシュを交互に利用しても強い権限のトークン・メタデータ・選択肢が弱いロールへ漏れないことを確認する。証明書失効時は該当プロファイルだけが安全に失敗することを確認する。

**合格条件:** トークンのRoleはマッピングで決まり、任意のクライアント入力で昇格できない。

### T-M03 — SuiteQLの行／型／列の権限制限

同じSQLを、全子会社参照、特定子会社限定、対象型権限なし、対象項目権限なし、部門等の制限あり、のロールで比較する。

一覧・件数・集計・詳細・明細・参照候補をすべて対象にする。返った0件が本当にデータなしなのか、権限制限なのかをテストデータから判定する。

**合格条件:** 型別に、行除外、列非公開、エラーと実コードを記録する。N/query専用オプションをRESTへ送って成立したことにしない。

## 6. N: 個別機能

### T-N01 — selectOptionsの契約

新規POST／既存PATCHを専用Accept付きで実行する。実行前後のレコード件数・内容も確認し、通常保存要求との混同がないことを確かめる。

候補数がページサイズを超える項目で、複数項目、limit/offset、qのCONTAIN/IS/START_WITHを試す。親項目・明細項目・ロールを変え、候補変化を記録する。未知の依存関係を「自動検出済み」と扱わない。

**合格条件:** 新規・既存の要求／応答の実物、フィールドごとのページング、依存設定、キャッシュキーが決まる。

### T-N02 — Actionと承認

Supported Record Actionsに掲載された、実アカウントで有効な承認対象を選ぶ。例はTimeBill。対応状態・必要権限・要求本文・200応答・通知・エラーを採取する。

受注のorderStatus PATCHは別ケースにし、カスタム承認ワークフローに対する正しい業務遷移かを確認する。

**合格条件:** Action名をUIラベルから推測していない。承認の応答型をVendor Payment confirmの例だけでboolean固定にしていない。

### T-N03 — 受注→請求書Transform

単一行、同一品目の複数行、部分出荷／既請求等の条件を分ける。ヘッダーのみ上書き、特定明細の数量／金額変更、部分明細を含む要求を試す。

Location、生成先ID、元明細キー、生成先明細キー、請求後残数を記録する。重複実行時に別請求書が作成されるかも検証用データで確認する。

**合格条件:** 変換元と変換先の行対応を明示でき、キーの誤流用やタイムアウト後の二重作成を防ぐ方針がある。

### T-N04 — 保存検索／Datasetの列と件数境界

通常列、カスタム列、参照列、数式、集計、null、空結果、Unicode、同名表示列を含む検索・Datasetを用意する。結果キーとJSON型を採取し、Designerに必要な明示型を決める。

ページサイズを変え、結果の全ページ、next/hasMore、offset条件、件数上限に達した時の応答を確認する。SuiteQLは別ケースとし、その100,000件制限を他経路の説明へ流用しない。

大規模境界試験に十分な検証データがなければ「未実施」とする。少数件の成功だけで100k/1mまで保証しない。

**合格条件:** 列契約、列変更検出、型変換、途中打切り表示、経路別の上限が決まる。

### T-N05 — enum／参照／カスタムリスト

真のenum、customerのentitystatus、1つ以上のcustomlistを対象とする。Metadata Catalog、通常GET、selectOptions、Records Catalog、SuiteQLのそれぞれを比較する。

非アクティブ化、名称変更、候補追加、ロール変更、既存データが持つ廃止済み候補を試す。設計時のスナップショットだけで既存値を誤削除しないことを確認する。

**合格条件:** 取得元と更新頻度、型、表示名、利用可能候補が区別され、全てをenumとして固定していない。
